# 推文工作流开发参考文档

> 项目定位：面向学院融媒体学生的多人在线推文协作工具（零门槛网页访问 + AI 写稿 + 规范检查 + 审核流转）。
> 本文档整理工作流每个环节可参考的开源项目、具体借鉴点及落地方式，作为开发依据。

## 一、共识决策记录

| 决策项 | 结论 |
|--------|------|
| 使用者 | 学院融媒体学生（多人），管理者统一管理 |
| 访问方式 | 部署成网站（Netlify 静态站 + Serverless Functions） |
| 身份体系 | 第一版无登录，使用**共享口令**进门保护 AI 额度；账号体系后置 |
| 数据库 | Supabase 免费版（Postgres） |
| AI 提供商 | 智谱 GLM / DeepSeek / 豆包 三家 Key 已有，做成可切换适配层 |
| 交付策略 | 最小可用版（MVP）先行，用一周收集反馈再迭代 |
| 已知情风险 | Netlify 国内访问时快时慢 |
| 图片 | 用户自备（搜图神器 https://www.soutushenqi.com/home ），AI 文生图后置 |

## 二、工作流步骤 × 参考对象总表

| 工作流步骤 | 首选参考 | 借鉴什么 | 落地方式 |
|-----------|---------|---------|---------|
| 1. 选题登记 | dsh-wewrite | 选题中心 + 一键进入管线 | 任务卡片表单（主题/类型/作者） |
| 2. AI 写稿 | dsh-wewrite | 六步管线引擎分层：AI 步骤调 LLM、确定性步骤纯代码 | Netlify Function 调用 AI 适配层 |
| 2.1 段落改写交互 | dsh-wewrite | 选中文字→浮条"AI 改写"，只重写选中段，Ctrl+Z 撤销 | 编辑器核心交互，直接复刻 |
| 2.2 提示词组织 | wechat-ai-writer | LangGraph 式分步提示词链 | 写稿/改标题/摘要 各自独立 prompt 模板 |
| 3. 规范检查（质量门禁） | dsh-wewrite | 门禁不通过阻断流转 + 可行动的失败引导 | 检查不过 → 不能推进到"审核"状态 |
| 3.1 规则来源 | 高校通用规范 | 字号14/行距1.5-2/称呼统一/责编署名 | 规则存数据库，可编辑配置 |
| 4. 编辑与预览 | dsh-wewrite | 双栏：左 Markdown 改稿、右微信预览实时渲染 | doocs/md 引擎渲染右侧预览 |
| 5. 排版导出 | doocs/md、wechat-format | Markdown→微信 HTML 排版引擎 | 复用现成库，富文本一键复制贴进秀米 |
| 6. 审核流转 | （无直接参考，自建） | 状态机：写稿→排版→审核→发布，批注/打回 | Supabase 表 + 状态字段，属于空白点 |
| 7. 多人共享 | （无直接参考，自建） | 共享口令 + 作者署名字段 | 口令校验放 Netlify Function 环境变量 |
| 8. AI 适配层 | dsh-wewrite | 多供应商 fallback 链 + 统一配置页 | 智谱/DeepSeek/豆包 三适配器 + 配置页（Key 回显掩码） |
| 9. 部署 | Netlify + Supabase 官方文档 | 静态站 + Functions + 免费数据库 | 单仓库：frontend/ + backend(functions)/ |

## 三、各参考项目详细说明

### 3.1 dsh-wewrite（首选，MIT 开源）

- 仓库：https://github.com/jerryjiao/dsh-wewrite
- 技术架构文档：仓库内 `docs/tech-architecture.md`（含 ADR-001~009 决策记录），模块划分直接参考

**核心可借鉴设计：**

1. **六步写作管线**：选题 → 大纲 → 成稿 → 质量门禁 → 排版渲染 → 配图
   - 关键原则："文本生成步骤调 LLM，确定性步骤纯代码执行"——省钱且稳定
   - 我们的对应管线：写稿（AI）→ 规范检查（纯代码）→ 导出（纯代码）
2. **质量门禁（对应规范检查器）**：
   - 成稿必须先过门禁（内容质量校验 + 格式一致性校验）
   - 门禁不通过 → 阻断推送路径，给出"可行动的失败引导"（告诉用户具体改什么）
   - 映射到我们：检查不过 → 卡片停留在"写稿"状态并显示整改清单
3. **AI 选中改写**：
   - 编辑器选中一段文字 → 浮条输入指令 → 只重写选中段落，其余不动
   - 四个快捷方向：更口语 / 精简一点 / 扩写细节 / 更有数据感
   - Ctrl+Z 可撤销
4. **双栏编辑器**：左侧 Markdown 编辑（CodeMirror），右侧微信预览实时渲染，"所见即所推"
5. **凭据管理**：密钥只落服务端、界面回显掩码、带"连接测试"按钮

### 3.2 doocs/md / lyricat/wechat-format（排版引擎）

- doocs/md：https://github.com/doocs/md
- wechat-format：https://github.com/lyricat/wechat-format

**借鉴点：**
- Markdown → 微信公众号特制 HTML 的转换规则（行内样式内联、微信白名单标签处理）
- 直接复用其转换核心库，避免自己踩微信编辑器过滤规则的坑
- 落地：导出环节调用该引擎生成富文本，学生一键复制进秀米微调

### 3.3 sendwealth/wechat-ai-writer（提示词组织）

- 仓库：https://github.com/sendwealth/wechat-ai-writer（LangGraph + GLM）

**借鉴点：**
- 分步提示词链的组织方式：每个环节（起标题/写摘要/润色/扩写）独立 prompt 模板
- 落地：我们的 AI 适配层按"动作"组织 prompt，而非一个大 prompt 全包

### 3.4 辅助参考

- **neurapress**（https://github.com/tianyaxiang/neurapress）：界面设计参考，现代化 Markdown 公众号编辑器
- **fushiping/OneClick-Viral-Article-6.14**：功能清单参考（敏感词审查、多标题生成），仓库 readme 已 404，仅作思路参考

## 四、技术架构（开发蓝图）

```
┌─ Netlify 静态托管 ──────────────────────────┐
│  frontend/  Vue3 + Vite                     │
│   ├─ 口令门（共享口令，存 localStorage）       │
│   ├─ 任务列表（作者署名/状态筛选）             │
│   ├─ 双栏编辑器（Markdown + 微信预览）         │
│   │   └─ 选中改写浮条（4 个快捷方向）          │
│   └─ 规范检查报告面板（可行动整改清单）         │
├─ Netlify Functions（backend/）──────────────┤
│   ├─ /api/verify   口令校验                  │
│   ├─ /api/tasks    任务 CRUD（连 Supabase）  │
│   ├─ /api/ai       AI 适配层（智谱/DeepSeek/豆包）│
│   │   └─ Key 在环境变量，永不下发前端          │
│   └─ /api/check    规范检查（纯代码规则引擎）   │
├─ Supabase（免费 Postgres）───────────────────┤
│   ├─ tasks 表：id/主题/类型/作者/状态/文稿/批注 │
│   └─ rules 表：规范规则（可编辑）              │
└─────────────────────────────────────────────┘
```

### 规范检查规则（第一版内置，可编辑）

- 正文字号 14px、行间距 1.5–2 倍、字间距 2 倍
- 称呼统一：文案中"我院/我专业"→ 具体学院名
- 文末责编署名格式："责编 | 姓名"
- 禁用词/敏感词扫描
- 图片规格：JPG/PNG、单张 ≤10MB、横图 4:3 或 16:9
- 状态流转门禁：检查不通过 → 不可推进到"审核"

## 五、Git 管理策略（重要节点提交规范）

仓库：本目录初始化 git；每个重要开发节点必须提交，保证可回溯。

### 提交时机（重要步骤）

| 节点 | 提交信息示例 |
|------|-------------|
| 参考文档完成 | `docs: 整理工作流参考文档与架构蓝图` |
| 设计文档定稿 | `docs: 系统设计文档（数据模型/页面/接口）` |
| 项目脚手架搭建 | `chore: 初始化 Vue3 前端与 Netlify Functions 骨架` |
| 每完成一个功能模块 | `feat: 任务 CRUD 与状态流转` / `feat: AI 写稿适配层` 等 |
| 每修复一个 bug | `fix: 修复xxx` |
| MVP 交付 | `release: MVP v0.1（写稿/检查/流转/导出）` |

### 规范约定

- 提交信息格式：`<type>: <中文描述>`，type 取 docs/feat/fix/chore/release
- 每次提交前跑通基本验证（前端能构建、函数无语法错误）再提交
- MVP 各功能模块独立提交，禁止把多个不相关改动混入一次提交
